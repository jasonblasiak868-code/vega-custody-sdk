# vega-custody-sdk — Capability Inventory

Every capability below is implemented in the published source under `src/vega_custody/` and demonstrated by the cited test file. The "why no policy" column explains why a prompt-level or policy-based approach cannot structurally provide the same guarantee — authority held outside the model, fail-closed mechanics, or physical replication cannot be replicated by instructions the model itself evaluates.

| Capability | Why no policy-or-prompt approach can provide it | Where enforced in code | Test demonstrating it | Honest limit |
|---|---|---|---|---|
| **Turn capsule with hash-linked chain** | A model can claim it "wrapped" a turn, but nothing in a prompt binds the model to an immutable, verifiable chain where any field change is detected. The prefix hash is a mechanical digest over the capsule's canonical form; the model cannot compute or enforce it on its own outputs. | `capsule/capsule.py` — `make()` computes `prefix_hash` over canonical JSON; `verify()` recomputes and compares; `verify_chain()` enforces predecessor linkage. | `test_capsule.py` (12 tests), `redteam_1_chain_and_capsule.py` (CapsuleAttacks) | Does not prevent the model from generating a different capsule offline and swapping it before `make()` is called. The chain only protects what was actually handed to `make()`. |
| **Append-only DAG with record-or-refuse** | A policy can say "do not delete logs," but the model (or an attacker with file access) can truncate, edit, or fork a file. Here, every write goes to ALL replicas under a cross-process lock, each write is read back byte-for-byte, and any failure rolls back every replica. A fork by a stale writer is refused because the on-disk size changed. | `dag/dag.py` — `Chain._append_locked()` writes to all replicas, reads back, rolls back on any mismatch; `Chain._load()` verifies replica byte-identity and internal consistency on open. | `test_dag.py` (record-or-refuse, unwritable replica, stale writer, tamper detection), `redteam_1_chain_and_capsule.py` (ChainAttacks) | A truncated chain that is internally consistent passes `verify()` unless an external head or minimum length is supplied. This is by design — the chain cannot self-prove it wasn't cut. |
| **Location DAG with mandatory read-back verification** | A policy can say "verify the file was saved," but nothing forces the verification to actually read the bytes and compare the hash. Here, a `LOCATION` entry is refused unless `readback_sha256` matches the content entry's `data_sha256` — the location chain literally cannot record a save that didn't verify. | `dag/locations.py` — `LocationChain.record_location()` checks `readback_sha256 == want` where `want` comes from the content entry's payload. | `test_dag.py` (wrong read-back refused, unknown content refused) | Only verifies the digest at write time. A later silent corruption of the stored file is caught by `audit()` or `load()`, not prevented. |
| **Ledger: single-use commitment mint (metadata + hash only)** | A policy can say "each approval is single-use," but the model or a compromised process can replay a commitment. The ledger enforces single-use mechanically: the leaf hash (SHA-256 of the canonical commitment) is the uniqueness key; a second `mint()` with the same leaf raises `LedgerRefused`. Parameters are refused by the allow-list — the commitment carries only metadata, never action parameters. | `ledger/ledger.py` — `Ledger.mint()` checks `leaf in self._leaves`; validates fields against `META_FIELDS`; rejects extra fields. `ReadOnlyLedger` exposes only `verify()` and `inclusion_proof()` — no `mint`. | `test_ledger.py` (duplicate mint refused, parameters refused), `redteam_2_ledger_and_store.py` (LedgerAttacks: ReadOnlyLedger cannot mint) | The ledger trusts whoever calls `mint()`. The `commitment_check` callback (for WCOMMIT) is the gate — if the commit step does not check a human signature, single-use is only as strong as the caller's discipline. |
| **Fail-closed verify (tamper → False, never exception)** | A policy can say "verify before acting," but a verification function that raises on tamper can be caught and ignored. `Ledger.verify()` returns `False` on ANY failure (chain broken, commitment not found, WCOMMIT signature invalid) — it never raises, so a caller that checks `if not ledger.verify(c): refuse` cannot accidentally pass on an exception. | `ledger/ledger.py` — `verify()` wraps all checks in `try/except` and returns `False`. | `test_ledger.py` (tampered replica makes verify fail closed), `redteam_2_ledger_and_store.py` | Returns `False` without distinguishing why. A caller that wants to know "chain broken" vs "not minted" must re-read the chain separately. |
| **Merkle batching + public witness (root only leaves machine)** | A policy can say "anchor to a public ledger," but nothing in a prompt limits what data leaves the machine. The witness interface only ever receives a 32-byte Merkle root (hex string). No commitment content, no metadata, no keys. The OpenTimestamps witness enforces HTTPS (or loopback HTTP), follows no redirects, caps receipt size. | `ledger/merkle.py` — domain-separated tree; `ledger/backend_timestamp.py` — `OpenTimestampsWitness` URL validation, `_NoRedirect` handler, `MAX_RECEIPT_BYTES`. | `test_ledger.py` (batch anchor, inclusion proof), `redteam_4_witness.py` (HTTPS-only, no redirects, root-only, oversize receipt refused) | `OpenTimestampsWitness` has NOT been run live from this SDK; treat as unverified until you have a stored receipt and have upgraded/verified it with the reference `ots` client. |
| **Three-source store: all-three-or-none with rollback** | A policy can say "write to three places," but partial writes succeed silently in most code. Here, `save()` writes to all three backends, reads back each, and ONLY then records the DAG entries. If ANY step fails, written files are deleted, a `SAVE_ABORTED` entry is recorded, and `StoreRefused` is raised. Nothing lands on one or two sources. | `store/store.py` — `ThreeSourceStore.save()` try/except: writes to all, reads back, records DAGs; on exception, deletes written files, records `SAVE_ABORTED`, re-raises. | `test_store.py` (corrupting backend, down backend, rollback), `redteam_2_ledger_and_store.py` (StoreAttacks: failing last source leaves no residue) | The rollback is best-effort: if a delete fails, the exception is caught and ignored. A source that accepts the write but later silently corrupts the file is caught by `audit()`/`load()`, not prevented. |
| **Provenance-completeness scoring (floor, not quality)** | A policy can say "track provenance," but nothing forces a score to exist or be checked. Every save MUST be scored; a scorer that returns `None` or no `score` key raises `StoreRefused`. The default scorer checks five provenance fields (source, license_class, data, timestamp, lineage) — this is a completeness floor, not a quality judgement. | `store/store.py` — `default_score()` returns `{"score": 0..1, "checks": {...}, "scorer": "default-provenance-v1"}`; `ThreeSourceStore.save()` validates score dict and enforces `min_score`. | `test_store.py` (unscored save refused, below-minimum refused) | A save with all five fields present scores 1.0 even if the fields are meaningless. Plug in your own scorer for quality. |
| **Bounded process execution with verified kill** | A policy can say "limit output and time," but `subprocess.run(capture_output=True)` buffers all output in memory (a flood exhausts memory before any cap checks), and a timeout kills only the direct child, not the tree. Here, output is read in chunks, capped at `cap+1` bytes/stream, the whole process tree is killed (Windows job object with kill-on-close, POSIX process group), and the kill is confirmed by `wait()`. | `proc.py` — `run_bounded()` chunked readers with cap, `kill_tree()` kills tree and confirms; `ProcessJob` uses Windows job object (active process limit, per-process memory limit, program started suspended) or POSIX process group. | `redteam_3_proc.py` (overflow capped + confirmed kill, timeout + confirmed kill, grandchild kill confirmed) | Process control, not an OS sandbox. Does not block files, network, or syscalls. A descendant that calls `setsid` on POSIX can leave the group — `survivors()` is the guard. Hostile code belongs in a VM or container. |
| **Safe paths: symlink-resolved containment, Windows device names refused** | A policy can say "stay in your folder," but a symlink in an untrusted repo can point outside, and Windows device names (`nul`, `com1`, etc.) or trailing dots/spaces create aliasing. `contained()` resolves symlinks via `os.path.realpath` and refuses unless the result stays inside `root`. `safe_name()` refuses device names, trailing dots/spaces, `..`, separators, control chars. | `safepaths.py` — `safe_name()`, `contained()`, `read_capped()`, `atomic_write()`. | `redteam_5_audit_findings.py` (C2_PlainNames: devices, trailing dots/spaces refused) | `contained()` on Windows uses `os.path.commonpath` which fails across drives (returns `False` → refused). A symlink that points to a different drive is refused. |

## This repo in the family predictive loop

The organism map (ORGANISM_MAP.md) describes two flows that never mix:

**AUTHORITY FLOW (down from the human):**
human signs a single-use commitment → jacket gates check it → contained execution (two-gate) → the action touches the world → **the record is written to custody**.

**DATA/KNOWLEDGE FLOW (up from the record):**
**custody records** → librarian distils lessons → dkg-lattice builds the knowledge graph (origin + licence per fact) → reasoning/galaxy forecast from the lattice → harness pre-registers predicted paths → metacog gates completion on evidence → feed/galaxy show it all to the human, who decides again.

**vega-custody-sdk is the centerpiece of the data/knowledge flow.** Every record in the family — every capsule, every DAG entry, every ledger mint, every store save, every location — lands here first. The chain of custody is the substrate from which all downstream learning, reasoning, and foresight derive.

- **Records** (capsules, DAG entries, ledger mints, store saves) are the raw, append-only, tamper-evident facts.
- **Lessons** (librarian) distil patterns from those facts — but only because the facts have origin, hash linkage, and location proofs.
- **Knowledge graph** (dkg-lattice) attaches origin and licence to every fact — but only because the record carried `metadata.source`, `metadata.license_class`, and the store scored for them.
- **Lattice foresight** (reasoning/galaxy) predicts steps ahead — but only because the graph has verifiable provenance.
- **Human decision** — the governance feed and galaxy show the human the full chain from commitment to record to forecast, so the next commitment is informed by what actually happened, not what the model says happened.

This kit does not do the distillation, the graph build, the forecasting, or the decision. It provides the **ground truth** that makes all of them possible without trusting the model, the vendor, or the project. If the record can be quietly edited, the loop is broken at the root. This kit's job is to make that impossible by mechanics, not by promise.
